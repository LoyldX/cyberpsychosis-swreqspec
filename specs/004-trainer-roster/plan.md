# แผนทางเทคนิค: Trainer Roster

## 1. สรุปแนวทาง

1. ฟีเจอร์นี้รองรับ `FR-ROST-01` ให้เจ้าหน้าที่/ผู้จัดการจัดการตารางเวลาเข้างานและเวลาสอนของเทรนเนอร์
2. ระบบต้องรองรับการสร้าง อ่าน ปรับปรุง ลบ และยกเลิกกะตาม `ASM-01`
3. ข้อมูลเวลาที่ผิดเงื่อนไขหรือทับซ้อนกันต้องถูกปฏิเสธและไม่บันทึกตาม `ASM-02`
4. Backend จะใช้ Go และ Gin ตาม `CON-TECH-01` และเก็บข้อมูลด้วย PostgreSQL ตาม `CON-DB-01`
5. Frontend จะใช้ React (Vite) ตาม `CON-TECH-02`; รายละเอียด schema, API และสิทธิ์ยังรอคำตอบ `Q-01` ถึง `Q-06`

## 2. เทคโนโลยีที่ใช้

| สิ่งที่เลือก | มาจาก | หมายเหตุ |
|---|---|---|
| Go | `CON-TECH-01` | ใช้พัฒนา Backend API |
| Gin | `CON-TECH-01` | ใช้ทำ HTTP routing และ handler |
| PostgreSQL | `CON-DB-01` | ใช้เก็บตารางงานเทรนเนอร์ |
| React (Vite) | `CON-TECH-02` | ใช้ทำเว็บแอปพลิเคชัน |
| `pgx/v5`, `golang-migrate`, `fetch`, `react-router`, `vitest`, `@testing-library/react` | ทีมเลือกเอง ไม่ได้มาจาก spec | อ้างอิงแนวทางร่วมใน `specs/000-shared/README.md`; ต้องตรวจความเหมาะสมก่อน implement |

## 3. โมเดลข้อมูล

ยังไม่กำหนด schema หรือฟิลด์จริงจนกว่าจะได้คำตอบ:

- `Q-01`: รูปแบบกะรายสัปดาห์หรือวันที่เจาะจง
- `Q-02`: เวลาเข้างานและเวลาสอนแยกกันหรือไม่ และความสัมพันธ์ของช่วงเวลา
- `Q-03`: semantics ของการปรับปรุงตาราง
- `Q-04`: การระบุตัวตนและสิทธิ์
- `Q-05`: ผลกระทบต่อคลาสที่ถูกจอง
- `Q-06`: การจัดการเมื่อ PostgreSQL ไม่ตอบสนอง

หลังได้คำตอบ จึงกำหนด entity ตารางกะที่รองรับ `FR-ROST-01`, `ASM-01`, `ASM-02` และการแยกข้อมูลของเทรนเนอร์แต่ละคนตาม `AC-ROST-04`

## 4. API / หน้าจอ

ยังไม่กำหนด method, path, input หรือ output จริงจนกว่าจะได้คำตอบ `Q-01` ถึง `Q-06` เพื่อไม่สร้างพฤติกรรมที่ไม่มีใน spec

ขอบเขตที่จะต้องออกแบบภายหลัง:

- หน้าจอแสดงและจัดการตารางงานของเทรนเนอร์ รองรับ `FR-ROST-01` และ candidate `UI-ROST-01`
- API สำหรับบันทึกและเรียกดูเวลาเข้างาน รองรับ `AC-ROST-01`
- API สำหรับบันทึกและเรียกดูเวลาสอน รองรับ `AC-ROST-02`
- API สำหรับปรับปรุงข้อมูลเดิม รองรับ `AC-ROST-03`
- การแยกข้อมูลตาม trainer ID และการป้องกันผลกระทบข้ามเทรนเนอร์ รองรับ `AC-ROST-04`
- การลบและยกเลิกกะ รองรับ `ASM-01`
- validation และ transaction เมื่อข้อมูลผิดเงื่อนไข รองรับ `ASM-02`

การล็อกอิน/สิทธิ์และการเชื่อมการจองคลาสจะยังไม่สร้างจนกว่าจะได้คำตอบ `Q-04` และ `Q-05` เพราะเกี่ยวข้องกับ Out of scope หรือการประสานกับ Spec 005

## 5. ตารางตรวจ Constraints

| Constraint ID | ถูกนำไปใช้ที่ไหนใน plan | สถานะ |
|---|---|---|
| `CON-DB-01` | PostgreSQL ในโมเดลข้อมูลและ persistence ของตารางงานเทรนเนอร์ | ใช้แล้ว; รายละเอียด schema ยังรอ `Q-01` ถึง `Q-03` |
| `CON-TECH-01` | Go/Gin ใน Backend API | ใช้แล้ว |
| `CON-TECH-02` | React (Vite) ในเว็บแอปพลิเคชัน | ใช้แล้ว |
| DOM | spec ระบุว่าไม่มี | ยังไม่ได้ใช้ เพราะไม่มี DOM ใน spec |
| IF | spec ระบุว่าไม่มี | ยังไม่ได้ใช้ เพราะไม่มี IF ใน spec |

## 6. แผนทดสอบจาก Acceptance Criteria

| AC ID | ชื่อ test | ทดสอบอย่างไร |
|---|---|---|
| `AC-ROST-01` | `TestAC_ROST_01_CreateWorkSchedule` | สร้างเวลาเข้างานของเทรนเนอร์ที่ยังไม่มีตาราง แล้วเรียกดูและตรวจว่าค่าถูกบันทึก; รูปแบบข้อมูลรอ `Q-01` และ `Q-02` |
| `AC-ROST-02` | `TestAC_ROST_02_CreateTeachingSchedule` | สร้างเวลาสอนของเทรนเนอร์ที่ยังไม่มีตาราง แล้วเรียกดูและตรวจว่าค่าถูกบันทึก; ความสัมพันธ์กับเวลาเข้างานรอ `Q-02` |
| `AC-ROST-03` | `TestAC_ROST_03_UpdateSchedule` | ปรับปรุงตารางเดิมแล้วเรียกดูซ้ำเพื่อยืนยันค่าใหม่; semantics ของการปรับปรุงรอ `Q-03` |
| `AC-ROST-04` | `TestAC_ROST_04_IsolateTrainerSchedules` | สร้างตารางของเทรนเนอร์ A และ B ปรับ A แล้วตรวจว่าข้อมูลของ B ไม่เปลี่ยน |

การทดสอบลบ/ยกเลิกและ validation จะเพิ่มในชุดทดสอบของ `FR-ROST-01` ตาม `ASM-01` และ `ASM-02` หลังทีมยืนยันรายละเอียดข้อมูลที่เกี่ยวข้อง

## 7. ลำดับงาน

1. รับคำตอบ `Q-01` และกำหนดรูปแบบช่วงเวลาให้รองรับ `FR-ROST-01`
2. รับคำตอบ `Q-02` และกำหนดความสัมพันธ์เวลาเข้างาน/เวลาสอน
3. รับคำตอบ `Q-03` และกำหนด semantics ของ create/update/delete/cancel ตาม `ASM-01`
4. รับคำตอบ `Q-04` และกำหนดขอบเขตการตรวจสิทธิ์โดยไม่ดึง login เข้ามาเกิน spec
5. รับคำตอบ `Q-05` ร่วมกับทีม Spec 005 ก่อนกำหนด validation หรือผลกระทบต่อคลาส
6. รับคำตอบ `Q-06` และกำหนด error handling/transaction เมื่อ PostgreSQL ไม่ตอบสนอง
7. ออกแบบ migration, model, API และหน้าจอโดย trace กลับไปยัง `FR-ROST-01`, `ASM-01`, `ASM-02`
8. เขียน tests ตาม `AC-ROST-01` ถึง `AC-ROST-04` และตรวจ `CON-DB-01`, `CON-TECH-01`, `CON-TECH-02`

## 8. สิ่งที่ยังไม่ทำ

| Open Question | สิ่งที่ยังไม่สร้างจนกว่าจะได้คำตอบ |
|---|---|
| `Q-01` รูปแบบตารางงานเป็นกะซ้ำรายสัปดาห์หรือวันที่เจาะจง | ยังไม่กำหนดฟิลด์วัน/วันที่และ recurrence ใน schema/API |
| `Q-02` เวลาเข้างานและเวลาสอนแยกกันหรือไม่ และเวลาสอนต้องอยู่ภายในเวลาเข้างานหรือไม่ | ยังไม่กำหนด entity ความสัมพันธ์และ validation ของสองประเภทเวลา |
| `Q-03` การปรับปรุงตารางเดิมต้องแทนที่ แก้เฉพาะรายการที่เลือก หรือเพิ่มช่วงเวลาใหม่ | ยังไม่กำหนด update semantics และ endpoint contract |
| `Q-04` เจ้าหน้าที่/ผู้จัดการล็อกอินอย่างไร และสิทธิ์ต่างกันหรือไม่ | ยังไม่สร้าง authentication/authorization สำหรับฟีเจอร์นี้ |
| `Q-05` ตารางที่แก้ทับซ้อนกับคลาสที่จองแล้วต้องอนุญาต ปฏิเสธ หรือแจ้งเตือน | ยังไม่สร้าง integration หรือ business rule ที่เชื่อมกับ Spec 005 |
| `Q-06` เมื่อ PostgreSQL ไม่ตอบสนอง ระบบต้องแสดงผลและรักษาข้อมูลที่กำลังแก้อย่างไร | ยังไม่กำหนด status code, retry, transaction failure behavior หรือ UI error state |

`AC-ROST-01` ถึง `AC-ROST-04` เป็นเกณฑ์ทดสอบที่ต้องรักษาไว้ แต่รายละเอียด input/output จะปิดหลัง Open Questions ได้คำตอบ
