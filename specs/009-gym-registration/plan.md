# แผน: ลงทะเบียนเข้าใช้ยิม (QR Code / ออนไลน์ล่วงหน้า)
Spec: `specs/009-gym-registration/spec.md` (Draft v2 — ยังไม่ผ่าน clarify, ทุก ID เป็น Candidate) | สร้างเมื่อ 4 ตุลาคม 2569 | หน้านี้เป็นผลลัพธ์ที่ AI ร่าง คนตรวจต้องยืนยัน และยังไม่ใช่แผนที่ทีมรับรอง

## 1. สรุปแนวทาง
ระบบรับการลงทะเบียนเข้าใช้ยิมด้วย QR Code (FR-REG-01) และการลงทะเบียนออนไลน์ล่วงหน้า (FR-REG-02) เป็น Candidate
ข้อมูลที่เก็บมีเพียงรหัสนักศึกษาและชื่อ-นามสกุลตาม DOM-REG-01 (Candidate)
เป้าหมายเวลาต่อคนตาม NFR-PERF-03 (Candidate) ยังเป็น TBD (Q11)
ทุกอย่างรอการยืนยันจากทีม (Q6, Q7, Q8, Q11, Q12) ไม่มี requirement ที่ยอมรับแล้วในฟีเจอร์นี้ จึงไม่เริ่มสร้างโค้ด

## 2. เทคโนโลยีที่ใช้
| สิ่งที่เลือก | มาจาก | หมายเหตุ |
|---|---|---|
| ฐานข้อมูลเชิงสัมพันธ์ | CON-DB-01 | ใช้เฉพาะถ้า Q8 ตอบว่าเก็บใน CON-DB-01 ชนิดรอ Q4 (ค่าเดาคือ PostgreSQL) |
| หน้าบ้าน: React (Vite) | ทีมเลือกเอง ไม่ได้มาจาก spec | ใช้กับหน้าจอลงทะเบียน UI-REG-01..04 (Candidate) |
| หลังบ้าน: Python FastAPI | ทีมเลือกเอง ไม่ได้มาจาก spec | ค่าเริ่มต้นของรายวิชา |

## 3. โมเดลข้อมูล
| Entity | ฟิลด์หลัก | รองรับ |
|---|---|---|
| Gym registration | student ID, full name, registered at, channel (QR / ออนไลน์) | DOM-REG-01 (Candidate), FR-REG-01, FR-REG-02 (Candidate), CON-DB-01 (ตาม Q8) |

- ไม่มีฟิลด์อื่น (เช่น เลขบัตรประชาชน อีเมล) เพราะ DOM-REG-01 จำกัดข้อมูลไว้เพียง 2 ฟิลด์
- ฟิลด์ channel ยังขึ้นกับ Q6 ว่าต้องมีทั้งสองช่องทางหรือไม่

## 4. API / หน้าจอ
| รายการ | Input / Output หลัก | รองรับ |
|---|---|---|
| POST `/gym/registrations` | student ID, full name / ผลการลงทะเบียน สำเร็จหรือไม่สำเร็จ | FR-REG-01, FR-REG-02, DOM-REG-01 (Candidate) |
| หน้าจอลงทะเบียน 2 ช่อง (UI-REG-01, Candidate) | รหัสนักศึกษา, ชื่อ-นามสกุล / ส่งข้อมูล | DOM-REG-01 (Candidate) |
| เข้าหน้าลงทะเบียนจาก QR Code (UI-REG-02, Candidate) | QR ที่จุดลงทะเบียน / เปิดหน้าลงทะเบียน | FR-REG-01 (Candidate), รอ Q6 |
| หน้าสำเร็จ/ไม่สำเร็จ (UI-REG-03/04, Candidate) | ผลการลงทะเบียน / ข้อความแสดงผล | FR-REG-01, FR-REG-02 (Candidate) |

## 7. ลำดับงาน
1. ตอบ Q12 ว่า Main Prior REQ คือลำดับความสำคัญสูงสุดหรือไม่ (ก่อนจัดลำดับฟีเจอร์)
2. ตอบ Q6 เรื่องช่องทางและผู้สแกน QR (FR-REG-01, FR-REG-02)
3. ตอบ Q7 เรื่องผู้ที่ไม่มีรหัสนักศึกษา (DOM-REG-01)
4. ตอบ Q8 เรื่องการเชื่อมกับการนับคนและ Excel และตอบ Q4 เรื่องชนิดฐานข้อมูล (CON-DB-01)
5. ตอบ Q11 เรื่องเป้าหมายเวลาและความยาวคิว (NFR-PERF-03)
6. สร้างโมเดลและ API หลังได้คำตอบ 2–4 (AC-REG-01..03, AC-REG-05)
7. ทดสอบเวลาและคิวหลังได้เกณฑ์จาก Q11 (AC-REG-04)
8. สร้างหน้าจอ UI-REG-01..04 และต่อกับ API จริง (Candidate, รอทีมยืนยัน)

## 8. สิ่งที่ยังไม่ทำ
- **Q6** การลงทะเบียนต้องมีทั้ง QR Code และออนไลน์ล่วงหน้าหรือเลือกอย่างเดียว / ใครสแกน / ทุกครั้งหรือครั้งเดียว
  ส่วนที่เกี่ยวข้องกับข้อนี้จะยังไม่สร้างจนกว่าจะได้คำตอบ (FR-REG-01, FR-REG-02, UI-REG-02, AC-REG-01, AC-REG-02)
- **Q7** ผู้ใช้บริการมีเฉพาะนักศึกษาหรือไม่ และผู้ไม่มีรหัสนักศึกษาลงทะเบียนอย่างไร
  ส่วนที่เกี่ยวข้องกับข้อนี้จะยังไม่สร้างจนกว่าจะได้คำตอบ (DOM-REG-01, UI-REG-01, AC-REG-03)
- **Q8** ข้อมูลลงทะเบียนเกี่ยวข้องกับการนับคนเข้ายิมและไฟล์ Excel เดิมหรือไม่
  ส่วนที่เกี่ยวข้องกับข้อนี้จะยังไม่สร้างจนกว่าจะได้คำตอบ (CON-DB-01, AC-REG-05)
- **Q11** เป้าหมายเวลาลงทะเบียนต่อคนและความยาวคิวสูงสุด
  ส่วนที่เกี่ยวข้องกับข้อนี้จะยังไม่สร้างจนกว่าจะได้คำตอบ (NFR-PERF-03, AC-REG-04)
- **Q12** "Main Prior REQ" หมายถึงลำดับความสำคัญสูงสุดหรือความต้องการเดิม
  ส่วนที่เกี่ยวข้องกับข้อนี้จะยังไม่สร้างจนกว่าจะได้คำตอบ (การจัดลำดับฟีเจอร์นี้)
