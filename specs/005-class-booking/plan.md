# แผนทางเทคนิค: จองคลาสออกกำลังกาย

## 1. สรุปแนวทาง
- [FR-BKG-01] สมาชิกที่ล็อกอินแล้วใช้เว็บเพื่อส่งคำขอจองคลาสที่ฟิตเนสเปิดให้เข้าร่วม
- [FR-BKG-01] ระบบใช้ข้อมูลคลาสที่สร้างไว้ก่อนแล้ว; การสร้างคลาสและกำหนดช่วงเปิดรับอยู่นอกขอบเขต
- [FR-BKG-02, DOM-BKG-01] API ตรวจความพร้อมของเทรนเนอร์ก่อนบันทึก แต่ยังไม่กำหนดนโยบายกะจนกว่าจะตอบ Q-08 ถึง Q-10
- [NFR-PERF-01] บันทึกการจองด้วย PostgreSQL transaction และควบคุมคำขอที่แข่งขันกันตาม AC-BKG-05
- [CON-TECH-01, CON-TECH-02] Backend เป็น Go/Gin และหน้าสมาชิกเป็นเว็บ React/Vite; รายละเอียดที่ติด Open Questions จะยังไม่สร้าง

## 3. โมเดลข้อมูล
| Entity / แหล่งข้อมูล | ฟิลด์หรือข้อมูลหลัก | รองรับ | ขอบเขตและสิ่งที่ยังรอคำตอบ |
|---|---|---|---|
| Class (ข้อมูลที่มีอยู่ก่อนแล้ว) | รหัสคลาส, รหัสเทรนเนอร์, เวลาเริ่มและเวลาจบ; วิธีระบุว่าเปิดรับยังไม่กำหนด | FR-BKG-01, FR-BKG-02, DOM-BKG-01 | ไม่สร้างข้อมูลคลาสในฟีเจอร์นี้; รูปแบบคลาส/จำนวนที่นั่งและผู้สร้างรอ Q-02, Q-03 |
| Booking | รหัสการจอง, รหัสคลาส, การอ้างถึงสมาชิก | FR-BKG-01, FR-BKG-02, NFR-PERF-01 | เจ้าของข้อมูลสมาชิกและความสัมพันธ์กับบัญชีรอ Q-06; พฤติกรรมคลาสเต็ม/จองซ้ำรอ Q-05 |
| ตารางงานเทรนเนอร์ (อ่านจาก spec 004) | ข้อมูลช่วงเวลาที่จำเป็นต่อการตรวจตาม DOM-BKG-01 | FR-BKG-02, DOM-BKG-01 | ใช้แหล่งข้อมูลที่ spec 004 ส่งมอบ ไม่สร้างตารางงานซ้ำ; แหล่งกะและกะพิเศษรอ Q-10 |

ฟิลด์ในตารางเป็นข้อมูลขั้นต่ำที่อนุมานจาก AC สำหรับวางแผน ไม่ใช่การยืนยัน schema; จะไม่เพิ่มฟิลด์หรือเลือกวิธีผูกสมาชิก/คลาสที่เกินกว่าคำตอบใน Q-02, Q-03 และ Q-06

## 4. API / หน้าจอ
| รายการ | Input / Output หลัก | รองรับ | ขอบเขต |
|---|---|---|---|
| `POST /api/bookings` (แนวทาง endpoint) | Input: รหัสคลาสจากผู้ใช้ที่ล็อกอิน; Output: ผลการจองและข้อมูลอ้างอิงการจอง | FR-BKG-01, FR-BKG-02, DOM-BKG-01 | ตรวจสิทธิ์จาก session ตาม precondition ของ spec 001; รูปแบบ error/response และการผูกสมาชิกยังรอ Q-05, Q-06, Q-07 |
| หน้าเว็บจองคลาส (React/Vite) | เลือกคลาสที่มีอยู่และส่งคำขอ; รายละเอียดผลลัพธ์รอคำตอบที่เกี่ยวข้อง | FR-BKG-01, CON-TECH-02 | ไม่รวมหน้าสร้างคลาส, ยกเลิก, หรือดูรายการจองทั้งหมดซึ่งอยู่นอกขอบเขต; การเรียกดูการจองใน AC-BKG-01 ขัดกับ Out of scope และรอ Q-04 |

ไม่มีการกำหนด endpoint แยกสำหรับตรวจ availability หรือหน้าจอ Candidate UI-BKG-01/02 เป็น requirement; รายละเอียดเหล่านี้ไม่เริ่มสร้างจนกว่าจะมีข้อกำหนดที่ยืนยันแล้ว

| AC-BKG-02 | `TestAC_BKG_02` | ใช้ PostgreSQL จริง สร้างคลาสเดิมและคำขอคลาสเวลาทับซ้อนของเทรนเนอร์เดียวกัน ตรวจว่ารายการใหม่ถูกปฏิเสธและไม่ถูกบันทึก; รายละเอียดชนิดคิวรอ Q-09 และนโยบายกะรอ Q-08 |

| AC-BKG-04 | `TestAC_BKG_04` | ใช้ตารางงานตามข้อมูลที่ทีมยืนยัน แล้วจองคลาสที่จบหลังกะ ตรวจว่าถูกปฏิเสธและไม่มี booking; รอ Q-08, Q-10 |

NFR-PERF-01 ไม่มีเกณฑ์เวลาเชิงตัวเลข จึงยังไม่มี assertion ด้าน latency จนกว่าจะตอบ Q-01; AC-BKG-05 ตรวจเฉพาะผล concurrency ที่ระบุไว้

## 7. ลำดับงาน
1. ตรวจสัญญาข้อมูล Class และตารางงานจาก preconditions ของ spec 004; ระงับการกำหนดผู้สร้าง/สถานะเปิดรับจนตอบ Q-03
2. ออกแบบ Booking และการอ้างถึงสมาชิกใน PostgreSQL ตาม FR-BKG-01/02 และ CON-DB-01; รอ Q-02, Q-05, Q-06
3. สร้าง migration และ store สำหรับ Booking ด้วย `pgx/v5`; รอข้อมูล schema ที่จำเป็นจากขั้น 2
4. สร้าง Gin endpoint รับคำขอจองและใช้ session ของสมาชิกตาม FR-BKG-01; รอ Q-05, Q-06, Q-07 และความขัดแย้งการเรียกดูใน Q-04
5. เพิ่มการตรวจคิวทับซ้อนและกะโดยอ่านข้อมูลจาก spec 004 ตาม FR-BKG-02/DOM-BKG-01; รอ Q-08, Q-09, Q-10
6. ทำ check-and-insert ใน PostgreSQL transaction พร้อมกลไก serialize คำขอต่อเทรนเนอร์สำหรับ NFR-PERF-01/AC-BKG-05
7. สร้างหน้าจอเว็บส่งคำขอจองและเชื่อม API ตาม FR-BKG-01/CON-TECH-02
8. เพิ่ม Go tests ตาม AC-BKG-01 ถึง AC-BKG-05 และ UI tests ที่ผูกกับ FR-BKG-01; รัน integration/concurrency tests กับ PostgreSQL จริงตาม `specs/000-shared/README.md` §3
