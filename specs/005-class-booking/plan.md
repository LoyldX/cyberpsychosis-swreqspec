# แผน: จองคลาสออกกำลังกาย
Spec: `specs/005-class-booking/spec.md` (Draft v1) | สร้างเมื่อ 4 ตุลาคม 2569 | หน้านี้เป็นผลลัพธ์ที่ AI ร่าง คนตรวจต้องยืนยัน

## 1. สรุปแนวทาง
ระบบแสดงคลาสที่เปิดรับและรับการจองจากสมาชิกตาม FR-BKG-01
ก่อนบันทึกการจอง ระบบตรวจความว่างของเทรนเนอร์ตาม FR-BKG-02 และกฎ DOM-BKG-01 (เวลาซ้อนและนอกกะ) โดยใช้โมเดลตารางงานจาก 004
ข้อมูลการจองเก็บใน relational DB ตาม CON-DB-01 (ชนิดรอ Q4)
การตอบสนองตาม NFR-PERF-01 วัดไม่ได้เพราะ latency ยังไม่กำหนด จึงยังไม่ตั้งค่าเวลาตอบสนองในโค้ด

## 2. เทคโนโลยีที่ใช้
| สิ่งที่เลือก | มาจาก | หมายเหตุ |
|---|---|---|
| ฐานข้อมูลเชิงสัมพันธ์สำหรับการจอง | CON-DB-01 | ยังไม่เลือก รอ Q4 (ค่าเดาคือ PostgreSQL) |
| หน้าบ้าน: React (Vite) | ทีมเลือกเอง ไม่ได้มาจาก spec | ใช้กับหน้าจองคลาส (ข้อเสนอ ยังไม่ยืนยัน) |
| หลังบ้าน: Python FastAPI | ทีมเลือกเอง ไม่ได้มาจาก spec | ค่าเริ่มต้นของรายวิชา |

## 3. โมเดลข้อมูล
| Entity | ฟิลด์หลัก | รองรับ |
|---|---|---|
| Class | `class_id`, `trainer_id` (อ้างอิงเทรนเนอร์), `open_status` (สถานะเปิดรับ), `start_at`, `end_at` (ช่วงเวลาของคลาส) | FR-BKG-01 |
| Booking | `booking_id`, `member_id` (อ้างอิงสมาชิก), `class_id` (อ้างอิงคลาส), `booking_status` (สถานะการจอง) | FR-BKG-01, CON-DB-01 |

- ตารางงานเทรนเนอร์ (ความว่างและเวลาสอน) ใช้โมเดลของ 004 ร่วมกัน ไม่สร้างซ้ำในฟีเจอร์นี้
- ฟิลด์ที่ผูกกับจำนวนผู้จองต่อคลาสยังไม่สร้างจนกว่าทีมจะตอบว่าคลาสเป็นกลุ่มหรือ 1 ต่อ 1
- ฟิลด์ `member_id` ขึ้นกับการตัดสินใจทีมเรื่องเจ้าของข้อมูลสมาชิก

## 4. API / หน้าจอ
| รายการ | Input / Output หลัก | รองรับ |
|---|---|---|
| GET `/classes?status=open` | ตัวกรองสถานะ / คลาสที่เปิดรับ | FR-BKG-01 |
| POST `/classes/{classId}/bookings` | รหัสสมาชิก / ผลการจองหรือเหตุผลที่ปฏิเสธ | FR-BKG-01, FR-BKG-02, DOM-BKG-01 |
| หน้าจอจองคลาส (ข้อเสนอ ยังไม่ยืนยัน) | คลาสที่เปิดรับ / สถานะการจองหรือเหตุผลที่ถูกบล็อก | FR-BKG-01, FR-BKG-02 |

## 7. ลำดับงาน
1. T-01 สร้าง model Class (รองรับ: FR-BKG-01, CON-DB-01; สถานะ: รอการตัดสินใจทีม: โครงโปรเจกต์ (ดูหมายเหตุ 001))
2. T-02 สร้าง GET คลาสที่เปิดรับ (รองรับ: FR-BKG-01; สถานะ: รอการตัดสินใจทีม: โครงโปรเจกต์ (ผ่าน T-01; ดูหมายเหตุ 001))
3. T-03 ตรวจการจองซ้อนและเวลานอกกะก่อนบันทึก (รองรับ: FR-BKG-02, DOM-BKG-01; สถานะ: รอการตัดสินใจทีม: รูปแบบช่วงเวลาและตารางงาน (004 T-01))
4. T-04 สร้าง model Booking และ POST การจองคลาส (รองรับ: FR-BKG-01, FR-BKG-02, DOM-BKG-01; สถานะ: รอการตัดสินใจทีม: คลาสเป็นกลุ่มหรือ 1 ต่อ 1; รอการตัดสินใจทีม: เจ้าของข้อมูลสมาชิก; รอการตัดสินใจทีม: รูปแบบช่วงเวลาและตารางงาน (004 T-01))
5. T-05 ทดสอบการจองพร้อมกันและเวลาตอบสนอง (รองรับ: NFR-PERF-01, FR-BKG-02; สถานะ: รอการตัดสินใจทีม: ค่า latency ของ NFR-PERF-01 (ยังไม่มีหมายเลข Q))
6. T-06 เชื่อม Booking กับฐานข้อมูลจริง (รองรับ: CON-DB-01; สถานะ: รอ Q4; รอการตัดสินใจทีม: วิธีรัน Redis และฐานข้อมูลสำหรับ test)
7. T-07 สร้างหน้าจองคลาสและเหตุผลที่ถูกบล็อกด้วยข้อมูลจำลอง (รองรับ: FR-BKG-01, FR-BKG-02; สถานะ: รอการตัดสินใจทีม: โครงโปรเจกต์ (ดูหมายเหตุ 001); รอการตัดสินใจทีม: ยืนยันข้อเสนอ UI หน้าจองคลาส (ดู Assumptions))
8. T-08 ต่อหน้าจองคลาสกับ API จริง (รองรับ: FR-BKG-01, FR-BKG-02, CON-DB-01; สถานะ: รอ Q4; รอการตัดสินใจทีม: ยืนยันข้อเสนอ UI หน้าจองคลาส; รอการตัดสินใจทีม: คลาสเป็นกลุ่มหรือ 1 ต่อ 1)

## 8. สิ่งที่ยังไม่ทำ
- **Q4** เลือก PostgreSQL หรือ MySQL: ส่วนเชื่อมฐานข้อมูลจริง (T-06, T-08) จะยังไม่สร้างจนกว่าจะได้คำตอบ
- ยังไม่มีหมายเลข Q: ค่า latency ของ NFR-PERF-01: ยังไม่สร้างการทดสอบเวลาตอบสนอง (T-05)
- ยังไม่มีหมายเลข Q: คลาสเป็นกลุ่มหรือ 1 ต่อ 1: ยังไม่สร้างการตรวจจำนวนผู้จองต่อคลาส (T-04)
- ยังไม่มีหมายเลข Q: ใครเป็นผู้สร้างคลาส: ไม่มี task สร้างคลาสในรอบนี้
- ยังไม่มีหมายเลข Q: ใครเป็นเจ้าของข้อมูลสมาชิก: ยังไม่สร้างฟิลด์ `member_id` จนกว่าทีมจะตัดสิน (T-04)
- ยังไม่มีหมายเลข Q: ข้อเสนอ UI หน้าจองคลาส: ยังไม่สร้างหน้าจอจนกว่าทีมจะยืนยัน (T-07, T-08)
