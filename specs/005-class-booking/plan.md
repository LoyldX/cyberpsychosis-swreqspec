# แผนทางเทคนิค: จองคลาสออกกำลังกาย

Spec: [`spec.md`](spec.md) (Draft v2 ผ่าน /clarify รอบ 2, อัปเดต 12 พฤศจิกายน 2569) — FR-BKG-01, FR-BKG-02, NFR-PERF-01, DOM-BKG-01, CON-DB-01 | กรอบร่วม: [`specs/000-shared/README.md`](../000-shared/README.md) | ร่าง: 12 พฤศจิกายน 2569 (AI ร่าง รอทีมตรวจ — แทนที่ plan ฉบับ 11 พฤศจิกายน 2569 ที่อิงคำถามซึ่งปิดแล้ว)

## 1. สรุปแนวทาง
- สมาชิกที่ล็อกอินแล้ว (001) เปิดหน้าเว็บ `/classes` เห็นคลาสกลุ่มที่ยังไม่ถึงเวลาเริ่ม เลือกแล้วกดจอง (FR-BKG-01, ASM-03, ASM-05)
- ข้อมูลคลาส (เทรนเนอร์ เวลาเริ่ม-จบ จำนวนที่นั่ง) เตรียมไว้ล่วงหน้าในตาราง `classes` ไม่มีหน้าจอหรือ API สร้างคลาส (ASM-04)
- `POST /api/bookings` ตรวจทุกเงื่อนไขแล้วบันทึกใน transaction เดียวของ PostgreSQL ถ้าไม่ผ่านจะปฏิเสธพร้อมรหัสเหตุผล และไม่บันทึกอะไรเลย (FR-BKG-02, DOM-BKG-01, ASM-05, ASM-07)
- กฎบล็อก: เวลาทับซ้อนกับคลาสอื่นของเทรนเนอร์คนเดียวกันที่มีผู้จองแล้ว (นับกรณีต่อกันพอดีด้วย) หรือคลาสอยู่นอกเวลาเข้างานของเทรนเนอร์จาก 004 (ASM-08..ASM-13)
- คำขอที่แข่งกันถูกเรียงคิวทีละเทรนเนอร์ด้วย advisory lock ภายใน transaction จึงสำเร็จได้เพียงรายการเดียวและตอบภายใน 1 วินาที (NFR-PERF-01, ASM-02, AC-BKG-05)

## 3. โมเดลข้อมูล
migration `0004_create_class_booking` (PostgreSQL, CON-DB-01)

| ตาราง | ฟิลด์ | รองรับ | หมายเหตุ |
|---|---|---|---|
| `classes` | `id BIGINT IDENTITY PK`, `trainer_id BIGINT NOT NULL`, `starts_at TIMESTAMPTZ NOT NULL`, `ends_at TIMESTAMPTZ NOT NULL`, `capacity INTEGER NOT NULL` — CHECK `ends_at > starts_at`, CHECK `capacity > 0`, index `(trainer_id, starts_at)` | FR-BKG-01, FR-BKG-02, DOM-BKG-01, ASM-03, ASM-04 | ข้อมูลเตรียมไว้ล่วงหน้า (ASM-04) `trainer_id` **ยังไม่มี foreign key** เพราะตารางเทรนเนอร์เป็นของ 004 ซึ่งยังไม่มี schema (ดู D1) ไม่มีฟิลด์ "สถานะเปิดรับ" เพราะ ASM-01 ถือว่าคลาสที่ยิมเตรียมไว้คือคลาสที่เปิดรับ |
| `bookings` | `id BIGINT IDENTITY PK`, `class_id BIGINT NOT NULL REFERENCES classes(id)`, `member_id BIGINT NOT NULL REFERENCES members(id)`, `created_at TIMESTAMPTZ NOT NULL DEFAULT now()` — UNIQUE `(class_id, member_id)` | FR-BKG-01, NFR-PERF-01, ASM-05, ASM-06 | `member_id` อ้าง `members` ของ 001 (ASM-06) ไม่เก็บข้อมูลส่วนตัวของสมาชิกซ้ำ UNIQUE กันจองคลาสเดิมซ้ำ (ASM-05) แม้มีคำขอแข่งกัน |
| เวลาเข้างานของเทรนเนอร์ | **ไม่สร้างในฟีเจอร์นี้** อ่านผ่าน interface `ShiftChecker` จากข้อมูลของ 004 | FR-BKG-02, DOM-BKG-01, ASM-11 | "จัดตารางเทรนเนอร์" อยู่ใน Out of scope ของ 005 รูปแบบข้อมูลรอ Q-01, Q-02 ของ 004 (ดู D6) |

ค่าที่คำนวณ ไม่เก็บเป็นฟิลด์: "คลาสเป็นคิวสอนแล้ว" = มีแถวใน `bookings` อย่างน้อย 1 แถว (ASM-10), "คลาสเต็ม" = จำนวนแถวใน `bookings` ของคลาส ≥ `capacity` (ASM-03)

## 4. API / หน้าจอ
ทุก endpoint อยู่หลัง `auth.RequireSession` ของ 001 ไม่มี header `Authorization: Bearer <token>` หรือ session ไม่ถูกต้องได้ `401 {"error":"unauthorized"}` และถ้า Redis มีปัญหาได้ `503` จาก middleware เดิม

| รายการ | Input / Output หลัก | รองรับ |
|---|---|---|
| `GET /api/classes` | Output `200` รายการ `{id, trainer_id, starts_at, ends_at, capacity}` เฉพาะคลาสที่ยังไม่ถึงเวลาเริ่ม เรียงตาม `starts_at`; `503 {"error":"unavailable"}` เมื่อ DB ล่ม | FR-BKG-01 (สมาชิก "เลือก" คลาส), ASM-05 |
| `POST /api/bookings` | Input `{"class_id": <int>}` (ผู้จองคือสมาชิกใน session) → `201 {id, class_id, member_id, created_at}`; `400 invalid_request`; `404 class_not_found`; `409` พร้อม `error` = `class_started` / `already_booked` / `class_full` / `trainer_off_shift` / `trainer_busy` และ `message` ภาษาไทย; `503 unavailable` (ไม่บันทึกอะไร) | FR-BKG-01, FR-BKG-02, DOM-BKG-01, NFR-PERF-01, ASM-05, ASM-07 |
| `GET /api/bookings/:id` | Output `200` การจองนั้นถ้าเป็นของสมาชิกใน session; `404 booking_not_found` ถ้าไม่พบหรือเป็นของคนอื่น; `503` | FR-BKG-01 (AC-BKG-01 "เรียกดูการจองนั้นได้") — ดูได้ทีละรายการเท่านั้น ไม่ใช่ "ดูรายการจองของตนเอง" ที่อยู่ใน Out of scope (Q-04) |
| หน้า `/classes` (React, ครอบ `RequireAuth`) | แสดงคลาสจาก `GET /api/classes` กดจองแล้วแสดงผล: สำเร็จแสดงการจองที่ได้ (ดึงซ้ำจาก `GET /api/bookings/:id`), ไม่สำเร็จแสดงข้อความตามรหัสเหตุผล | FR-BKG-01, CON-TECH-02, ASM-05 |

ไม่ทำ: หน้าหรือ API สร้างคลาส (ASM-04), ยกเลิกการจองและดูรายการจองทั้งหมด (Out of scope, Q-04), endpoint ตรวจ availability แยก และการซ่อนคลาสที่ถูกบล็อกล่วงหน้า (UI-BKG-01/02 เป็นแค่ Candidate)

## 7. ลำดับงาน
1. migration 0004 ตาราง `classes`, `bookings` (CON-DB-01, FR-BKG-01)
2. กฎล้วน: ช่วงเวลาทับซ้อนแบบปิดและอยู่ในกะ (AC-BKG-02..04, ASM-12, ASM-13)
3. store: รายการคลาสที่ยังไม่เริ่ม อ่านการจองของสมาชิก และ transaction จอง (advisory lock ต่อเทรนเนอร์ ตรวจไม่พบ/เริ่มแล้ว/ซ้ำ/เต็ม/ทับซ้อน) (FR-BKG-01, FR-BKG-02, ASM-05)
4. service: `Clock`, `ShiftChecker` และลำดับการตรวจ (DOM-BKG-01, ASM-08, ASM-11)
5. Gin handler + route 3 endpoint หลัง `RequireSession` (AC-BKG-01..04)
6. test จองพร้อมกัน AC-BKG-05 (NFR-PERF-01)
7. หน้าเว็บ `/classes` ด้วย API จำลอง (FR-BKG-01, CON-TECH-02)
8. ตัวอ่านเวลาเข้างานจาก 004 (รอ 004)
9. ประกอบเข้ากับ `cmd/api/main.go` แล้วต่อหน้าเว็บกับ API จริง + ข้อมูลคลาสตัวอย่าง + ตรวจด้วยมือ (รอข้อ 8)
10. เขียน `docs/API.md` หัวข้อ 005 (README ขั้นที่ 5)

### 8.2 ข้อเสนอการออกแบบที่ทีมต้องยืนยัน (ทีมเลือกเอง ไม่ได้มาจาก spec)
| # | ข้อเสนอ | เหตุผล | ความเสี่ยง |
|---|---|---|---|
| D1 | `classes.trainer_id` ไม่มี foreign key จนกว่า 004 จะมีตารางเทรนเนอร์ | 004 ยังไม่มี schema และ 005 สร้างตารางเทรนเนอร์เองไม่ได้ (Out of scope) | ใส่ `trainer_id` ที่ไม่มีอยู่จริงได้ ต้องเพิ่ม FK ใน migration ภายหลัง |
| D2 | `pg_advisory_xact_lock` ต่อ `trainer_id` ภายใน transaction จอง + UNIQUE `(class_id, member_id)` | AC-BKG-05: คำขอที่แข่งกันของเทรนเนอร์เดียวกันต้องผ่านทีละรายการ และกันจองซ้ำแม้ยิงพร้อมกัน | คำขอของเทรนเนอร์คนเดียวกันรอคิวกัน (ยอมรับได้ที่ขนาดยิม) |
| D3 | ลำดับตรวจเมื่อผิดหลายข้อ: ไม่พบคลาส → เริ่มแล้ว → จองซ้ำ → เต็ม → นอกกะ → ทับซ้อน ตอบเหตุผลข้อแรกที่เจอ | spec ไม่กำหนดลำดับ เลือกจากข้อที่ไม่ต้องอ่านข้อมูลอื่นก่อน | ผู้ใช้เห็นเหตุผลเดียวแม้ผิดหลายข้อ |
| D4 | `GET /api/classes` แสดงเฉพาะคลาสที่ยังไม่ถึงเวลาเริ่ม และไม่แสดงจำนวนที่นั่งเหลือ | ASM-05 ปฏิเสธคลาสที่เริ่มแล้ว จำนวนที่นั่งเหลือไม่มีใน spec | สมาชิกรู้ว่าคลาสเต็มเมื่อกดจองแล้วเท่านั้น |
| D5 | `GET /api/bookings/:id` ดูได้ทีละรายการและเฉพาะของตนเอง ของคนอื่นตอบ `404` | AC-BKG-01 ต้อง "เรียกดูการจองนั้นได้" แต่ "ดูรายการจองของตนเอง" อยู่ใน Out of scope | ทีมอาจมองว่าใกล้เคียงกับ Q-04 ต้องยืนยัน |
| D6 | interface `ShiftChecker` (ถามว่าช่วงเวลาของคลาสอยู่ในเวลาเข้างานของเทรนเนอร์ทั้งหมดหรือไม่) ไม่มีข้อมูลกะ = นอกกะ = บล็อก; ตัวอ่านจริงจากตาราง 004 ทำทีหลัง | รูปแบบตาราง 004 ยังไม่รู้ (004 Q-01, Q-02) แต่กฎของ 005 ตัดสินแล้ว (ASM-08, ASM-11, ASM-13) | ก่อน 004 เสร็จ ระบบจริงจองไม่ได้เลยเพราะไม่มีข้อมูลกะ (จึงยังไม่ประกอบเข้า `main.go`) |
| D7 | ใช้ `fetch` + `useEffect` ไม่ใช้ react-query | ดูข้อ 2 | ต่างจาก `000-shared` §2 |
| D8 | test ที่ใช้ DB ล้างตาราง `bookings` และ `classes` ก่อน/หลังแต่ละ test ในฐานข้อมูลเดียวกับ dev | ตามแบบ test ของ 006/007 | ข้อมูลคลาสตัวอย่างใน dev หายเมื่อรัน test |
| D9 | ข้อมูลคลาสตัวอย่างสำหรับ dev อยู่ในไฟล์ SQL แยก (`backend/seeds/005_classes.sql`) รันด้วยมือ ไม่ใส่ใน migration | ASM-04 ให้เตรียมข้อมูลไว้ล่วงหน้า แต่ข้อมูลตัวอย่างไม่ควรเข้า production ผ่าน migration | ต้องใช้ `trainer_id` ที่ตรงกับข้อมูลของ 004 |
