# Feature: รักษา Session Login แบบ Persistent
Spec ID: FR-AUTH-01, NFR-REL-01, CON-CACHE-01 | Source: `docs/srs/srs.md` (v5) | Status: Draft v1 | อัปเดต: 4 ตุลาคม 2569

## Goal
สมาชิกต้องสามารถเข้าสู่ระบบและใช้งานต่อเนื่องได้โดยไม่ต้องทำการล็อกอินซ้ำบ่อยครั้ง ระบบจะบำรุงรักษา Session โดยใช้ Refresh Token และ Redis เพื่อให้ Refresh Token มี TTL 7 วัน และลดปัญหา Auto-logout ที่ทำให้ผู้ใช้รู้สึกว่าระบบขาดความต่อเนื่อง (pain point ข้อ 2 ใน refine-req §1)

การเข้าสู่ระบบหลักของสมาชิกคือการใช้งานด้วยรหัสนักศึกษา/SSO ตามลำดับความเหมาะสมของระบบและบริบทของผู้ใช้ โดยไม่ใช่การให้ผู้ใช้กรอกข้อมูลซ้ำเป็นประจำ

## Scope
### In scope
- FR-AUTH-01 รองรับการเข้าสู่ระบบของสมาชิกและรักษา session แบบ persistent ด้วย refresh token
- NFR-REL-01 การจัดการ session ผ่าน Redis ร่วมกับ refresh token
- CON-CACHE-01 ใช้ Redis บริหาร session login
### Out of scope
- ตัดออกทั้งระบบ (refine-req §2.1–2.2): POS และการขายหน้าร้าน; เครื่องสแกนเวลาและการซิงค์ HR; Data Privacy & Encryption (TLS 1.3, AES-256, PDPA); Nutrition (FR-NUT-01, IF-NUT-01); ระบบเช็กสถานะเครื่องเล่นและคิวเครื่องเล่น (Q10)

## Constraints
- CON-CACHE-01 ใช้ Redis สำหรับบริหาร session login

## Requirements (ยอมรับแล้ว)
| ID | ข้อกำหนด |
|---|---|
| FR-AUTH-01 | **รักษา Session Login แบบ Persistent**: สมาชิกสามารถเข้าสู่ระบบด้วยรหัสนักศึกษา/SSO เป็นหลัก และยังคงใช้งานต่อเนื่องได้โดยไม่ต้องกรอกข้อมูลล็อกอินซ้ำภายในช่วงที่ระบบกำหนด โดยระบบใช้ Refresh Token เพื่อยืดอายุ session และลดการถูก Auto-logout บ่อยครั้ง สำหรับกรณีที่ session หมดอายุก่อนกำหนด ระบบจะใช้ refresh token เพื่อต่อ session แทนการให้ผู้ใช้เข้าสู่ระบบใหม่ทั้งหมด และ Refresh Token มี TTL เท่ากับ 7 วัน |

## Quality Requirements (ยอมรับแล้ว)
| ID | ข้อกำหนด |
|---|---|
| NFR-REL-01 | Session Persistence & Reliability: การจัดการ Session ผ่าน Redis ร่วมกับ Refresh Token ต้องให้จำนวนครั้งที่หลุดจากระบบโดยไม่ตั้งใจอยู่ในระดับที่ยอมรับได้ และต้องสามารถยืนยัน/ตรวจสอบ session state ได้ภายในสภาพแวดล้อมที่ระบบใช้งานจริง — Refresh Token TTL = **7 วัน** และอัตราหลุดสูงสุด = **TBD** |

## Clarification Notes
- ข้อความใน requirement นี้ยึดว่า “session แบบ persistent” หมายถึงการให้ผู้ใช้สามารถเข้าถึงแอปต่อเนื่องได้โดยไม่ต้องกรอกข้อมูลเข้าสู่ระบบซ้ำภายในระยะเวลา 7 วันของ Refresh Token ตามที่กำหนดแล้ว
- การเลือกใช้งาน “รหัสนักศึกษา/SSO” เป็นวิธีเข้าสู่ระบบหลักได้รับการยืนยันแล้วจากทีม และเป็นทางเลือกที่ใช้งานแทนการลงทะเบียนแบบ manual หรือการป้อนข้อมูลซ้ำเป็นประจำ
- ข้อความด้านการใช้ Refresh Token และ Redis เป็นการกำหนดเทคโนโลยี/สถาปัตยกรรมที่ยอมรับแล้วตาม CON-CACHE-01 และไม่ใช่การตัดสินใจเรื่อง UX หรือ business rule ใด ๆ ที่ไม่ถูกระบุไว้ใน spec

## Assumptions & Open Questions
- **Q2 (Resolved)** "User" ที่โดน Auto-logout คือสมาชิกทุกคน และ Refresh Token TTL ถูกกำหนดเป็น 7 วัน โดยให้ผู้ใช้สามารถใช้งานต่อเนื่องได้โดยไม่ต้องกรอกข้อมูลล็อกอินซ้ำภายในช่วงเวลานั้น ผู้ตอบที่น่าจะได้: ทีม Mobile App / Product Owner
- **Q7** ผู้ใช้บริการมีเฉพาะนักศึกษาหรือไม่ และผู้ใช้ที่ไม่มีรหัสนักศึกษา (เช่น บุคลากร บุคคลภายนอก) ลงทะเบียนอย่างไร (ยังไม่มีคำตอบ ค่าเดา: มีเฉพาะนักศึกษา ผู้ตอบที่น่าจะได้: ผู้ดูแลยิม) เกี่ยวกับ FR-AUTH-01
- ผลต่อ FR-AUTH-01: วิธีเข้าสู่ระบบของผู้ไม่มีรหัสนักศึกษา
- การเข้าสู่ระบบหลักเป็นวิธีใช้รหัสนักศึกษา/SSO แล้ว ตามการยืนยันของทีม โดยไม่มีการวางแผนให้ใช้วิธีการล็อกอินแบบ manual ที่ต้องกรอกข้อมูลซ้ำเป็นประจำ
- ยังไม่มีหมายเลข Q: ใครเป็นเจ้าของข้อมูลสมาชิก (member record) เพราะ 001, 003 และ 005 อ้างถึงสมาชิก
- คำถามข้อเสนอ UI (ไม่มี ID): เมื่อเปิดแอปภายในอายุ session ควรให้เข้าใช้งานได้ทันทีโดยไม่ต้องกรอกข้อมูลล็อกอินซ้ำหรือไม่? (ยังไม่มีหมายเลข Q เกี่ยวข้องกับ Q2)
- หมายเหตุ: ระยะเวลา Refresh Token TTL ได้รับการกำหนดแล้วเป็น 7 วัน และจะใช้เป็นค่าพื้นฐานสำหรับการพัฒนาระบบ
